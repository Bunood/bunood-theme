# Bunood Sellable MVP PRD

**Target pilot date:** 2026-09-18  
**Product:** Bunood, an Arabic-first task-oriented operating layer on ERPNext  
**Release type:** controlled paid pilot, not general availability

## 1. Product outcome

A small business must be able to sign in, understand where to start, create the
minimum master data, quote a customer, turn the quotation into an invoice, record
payment, and produce a professional bilingual invoice without learning ERPNext's
full information architecture.

The MVP is sellable when that revenue path works reliably for a trained pilot user.
The complete product will continue shipping behind the same ERPNext data model while
real customer feedback determines which workflows deserve the next simplified surface.

## 2. Target customer and job

The first customer is a Saudi small business or property operator with a simple
sales workflow, one configured company, a small catalogue, and a limited number of
sales users. Their primary job is: **quote, invoice, collect, and print with minimum
training in Arabic or English.**

## 3. Tomorrow's MVP scope

| Capability | Acceptance criterion |
|---|---|
| Stable shell | One top bar and one standardized sidebar appear consistently on Home, app pages, lists, and forms in LTR and RTL. |
| Action-first home | A sales user can reach Customer, Item, Quotation, Sales Invoice, and Payment Entry without hunting through modules. |
| Customer and Item setup | Required fields are present in Simple mode; native validation, Quick Entry, permissions, and naming remain authoritative. |
| Quotation to invoice | A submitted, valid Quotation shows **Create Sales Invoice** and uses ERPNext's native mapping. |
| Direct invoice entry | The first blank item row is already visible. Item search happens in the Item cell; no separate Add Item gate exists. Additional rows use **Add line**. |
| Invoice lifecycle | Save draft, submit, delete draft, print, reload, discounts, taxes, totals, and stock choices use native ERPNext document behavior. |
| Payment | A submitted invoice exposes native **Payment**, leading to Payment Entry where Mode of Payment is recorded. No parallel payment ledger is introduced. |
| Print/PDF | The configured invoice format prints/PDFs with correct company identity, totals, VAT presentation, and Arabic/English direction. |
| Bilingual operation | Launch-path labels and controls are understandable in Arabic and English; RTL direction does not reverse semantic actions incorrectly. |
| Safety | Roles and field permissions are enforced; drafts do not post ledgers; submission remains the only accounting/stock posting boundary. |

## 4. Explicitly outside tomorrow's scope

- A replacement accounting engine, inventory engine, permission system, or ledger.
- Automatic payment posting from an unsaved or submitted invoice.
- Bank import, reconciliation automation, AI/OCR expense capture, payroll, and full
  manufacturing simplification.
- A simultaneous split-screen live print preview. Print/PDF is sufficient for the
  pilot; live preview is a post-launch usability enhancement.
- Simplified handling for returns, amendments, debit/credit notes, POS invoices, or
  mapped delivery/order allocation. These continue in the native Advanced form.
- General-availability scale, self-service onboarding, or zero-touch support.

## 5. UX contract

1. Simple mode is task-first; Advanced mode reveals the same native document.
2. No data is copied when modes change.
3. One visible action must correspond to one understandable business outcome.
4. Required fields cannot be hidden in Simple mode.
5. Desktop and mobile preserve the same action order and document state.
6. Arabic and English share structure; direction changes placement, not meaning.
7. A user can always recover: errors stay beside the field, drafts remain drafts,
   and risky deletion or reload actions require confirmation.

## 6. Architecture design

### Requirements summary

| Requirement | Architecture decision |
|---|---|
| Ship rapidly without corrupting ERP behavior | Extend native Frappe forms and controllers; do not fork transactional logic. |
| Simplify many document types | Shared Simple/Advanced adapter with explicit profiles and required-field fallback. |
| Consistent navigation | One registry-driven sidebar and one top-bar contract. |
| Fast invoicing | A Sales/Purchase Invoice workbench bound directly to the current `frm.doc`. |
| Safe conversion | ERPNext's whitelisted Quotation mapper. |
| Saudi operation | Native taxes plus the existing Bunood ZATCA facade and print formats. |

### App structure

```text
Frappe Desk + ERPNext
        |
        +-- bunood_theme
        |     +-- canonical shell/sidebar/top bar
        |     +-- role home and app dashboards
        |     +-- Simple/Advanced document adapter
        |     +-- invoice workbench
        |     +-- print and ZATCA presentation/facade
        |
        +-- setup / real-estate apps
              +-- native DocTypes, workflows, permissions, reports
```

### App inventory

| App/layer | Responsibility | Ownership rule |
|---|---|---|
| Frappe | Desk, metadata, permissions, controls, routing | Never bypass. |
| ERPNext | sales, purchasing, stock, accounting, mapping, posting | Native APIs remain authoritative. |
| `bunood_theme` | navigation and simplified task surfaces | Presentation/orchestration only. |
| Real-estate app | Property, Unit, Lease domain records | Domain app owns schema and workflow. |

### Data model

The MVP adds no parallel transactional schema. Customer, Item, Quotation, Sales
Invoice, Sales Invoice Item, Payment Entry, tax templates, warehouses, and price
lists remain native ERPNext records. Property/Unit/Lease remain in their owning app.
Theme settings store presentation preferences only.

### Cross-app communication

- Browser controls update the active Frappe form through native model setters.
- Save/submit use the active form's native methods.
- Quotation conversion calls ERPNext's native mapped-document endpoint.
- Payment calls the native invoice controller and Payment Entry mapping.
- ZATCA calls the existing credential-free Bunood server facade; credentials are not
  exposed to the browser.

### ERPNext extensions

Extensions are hooks, presentation adapters, settings, reports, print formats, and
facades. There is no fork of general-ledger posting, stock posting, tax calculation,
or permission evaluation.

## 7. Launch gate

The pilot may start only when all launch-path automated tests pass, production assets
build, the local site serves the new bundle, and a human smoke test completes this
sequence in both directions: Home → Customer/Item → Quotation → Sales Invoice → Save
→ Submit → Payment → Print. Any accounting-posting or permission regression is a
release blocker. Cosmetic issues outside that path are triaged after the pilot begins.

## 8. Success measures for the first seven days

- A new trained user creates and saves a correct invoice in under five minutes.
- At least 90% of pilot invoices are created without switching to Advanced mode.
- Zero duplicate invoices, orphan payments, permission bypasses, or posting defects.
- Every blocking issue has a reproducible route, role, language, and document state.
- Customer feedback is reviewed daily and ranked by revenue-path impact.

## 9. Commercial operating conditions

Tomorrow's sale should be described as a **founding-customer pilot** with controlled
onboarding, an agreed support channel, daily backups, and rapid fixes. Do not promise
full ERP module parity. Sell the completed quote-to-cash outcome and the right to
shape the broader product.
