# Engineering Guidelines — Bunood Theme

> **What this is.** The practices we hold this repo to, plus a verified audit of where
> it currently stands against them. Written 2026-08-03.
>
> **Why it exists.** `ARCHITECTURE.md` says how the theme is built; `CHANGELOG.md` says
> what changed. Neither says *how we decide* — which rules are mechanized, which are
> still honour-system, and what the open defects are. That gap is where drift lives.
>
> **How to read it.** Part 1 is the working doctrine. Part 2 is the audit, with the
> evidence attached, because a guideline nobody checked is just an opinion. Part 3 is
> the general practice catalogue this was drawn from, condensed to titles.
>
> **Standing rule for this document:** every claim of absence here was verified by
> grep or by reading the file, and the check is recorded. If you find one that is
> wrong, fix the document — a stale audit is worse than no audit, because it spends
> credibility it hasn't earned. This document has already been wrong once; see §2.0.

## Part 1 — How we work

Ordered by when the decision is available to you, because that determines what it
costs. Rules are grouped by whether a machine enforces them.

### 1.1 The rules a machine enforces (do not rely on memory for these)

| Rule | Mechanism | Where |
|---|---|---|
| No physical CSS properties — RTL safety | SCSS build **fails** on `left`/`right`/`margin-left`/… | `build.mjs`, run in CI |
| Committed `dist/` matches sources | `git status --porcelain` drift gate (not `git diff` — see below) | `.github/workflows/ci.yaml` |
| Shipped JS parses | `node --check` per file | `ci.yaml` |
| Shipped Python parses | `python3 -m compileall` | `ci.yaml` |
| Console stays quiet | error-budget test with an explicit allowlist | `tests/smoke.mjs` |
| Behaviour of every kit | 94-test Playwright suite | `tests/smoke.mjs` |
| Test signal isn't corrupted by its own tooling | `npm run verify` — one command, the suite's own exit code | `tools/verify.mjs` |
| A native affordance is hidden only once we replaced it | build **fails** on `display:none` of a native keyed on `data-bnd-layout`/`data-bnd-search` instead of `data-bnd-own` | `build.mjs` |
| Every component has an identity, and every identity is real | build **fails** on a registry entry with no `part`, or a `data-bnd-part` the registry never defined | `build.mjs` + `registry.py` |
| Settings fields are `<component>_<property>` | build **fails**, with a listed and shrinking exceptions set | `build.mjs` |
| No literal duration reaches compiled CSS — the reduced-motion zero actually zeroes everything | build **fails** on a hardcoded `transition`/`animation` time outside `--bnd-dur-*` | `build.mjs` |
| Every control our JS constructs has a `:focus-visible` rule, directly or via a co-class | build **fails** on a `bnd-*` control class no compiled selector covers | `build.mjs` |
| No two pieces of our chrome occupy the same pixels; no ragged rows; no unhittable control | layout-invariant helper, run across four layouts | `tests/smoke.mjs` |
| Every token pair clears WCAG 2.2 AA, **for any brand seed a tenant can enter** | 1,656 pairs recomputed over 11 seeds × 2 modes + the no-brand-sheet fallback (item 22 added the sidebar pill/mark/stand-down rows); `_tokens.scss` asserted equal to `palette.derive()` | `tools/contrast_gate.py`, run in CI as `npm run contrast` |
| The contrast model still describes the actual desk | rendered `getComputedStyle` values fed back to the same Python implementation | `tests/smoke.mjs` |
| The settings form's structure cannot change silently | committed shape fixture — node sequence, svg count, text length | `tests/fixtures/picker-shape.json`, regenerated by `tools/fingerprint.mjs` |
| Safety invariants hold in every reachable configuration | invariant matrix over layouts × styles × placements | `tests/smoke.mjs` |

Five of those were added on 2026-08-02/03, each **negative-tested** — the mechanism
was run against a deliberately broken build and had to fail before it was trusted.
That is not ceremony: three separate versions of the layout-invariant helper read as
correct and asserted nothing, the verify wrapper miscounted one failure as two, and
the shape fixture reported drift in a picker nobody had touched. All three were found
by breaking something on purpose, none by reading the code.

The `git status` versus `git diff` detail is the model for this whole section. A
rebuilt dist file gets a **new hashed name**, so it is untracked, and `git diff` never
reports untracked files. With `diff` alone, `git commit -am` stages the old file's
deletion but not the new one — shipping a tree with no theme JS while CI stays green.
That was reproduced end to end in release review v0.6.2..HEAD. The rule is not "be
careful when committing"; the rule is that the gate had to be built to catch the
specific way being careful fails.

Same lesson in `tools/verify.mjs`: `grep -c` prints `0` and **exits 1** when it finds
nothing, which is the good outcome — so a fully green run (92/92, exit 0) was reported
as failed. Diagnostics bolted on after a signal can invert it. Measure with something
that cannot change the verdict.

### 1.2 Before you write the CSS

- **Decide whether it's a one-way or two-way door.** Ship the simple version when the
  fix is a rule; think first when the fix is a token rename, a public class name, or
  anything Layer 3/4 consumes. Token names are an API — see 1.4.
- **Sketch the failure first.** What does this look like when the asset 404s, when the
  brand seed is a light yellow, when the string is Arabic, when the viewport is 375px,
  when the user is on `prefers-reduced-motion`? Failure behaviour retrofitted later
  usually needs state the happy path never made room for.
- **Prefer a token remap over a component selector.** Frappe class names are not a
  contract; CSS variables are the closest thing to one. A selector that depends on
  `.btn` surviving an upstream bump breaks silently.
- **Never touch Frappe-generated DOM.** Desk is coloured through tokens only. Our own
  components (`.bnd`/`.bnd-ck`, the palette, inbox, breadcrumbs, cluster) are the only
  markup we own — which is also the only place accessibility is fully ours. See 1.5.

### 1.3 Writing it

- **No raw `#hex` or `px` inside a rule.** Every colour, space, radius, shadow and
  duration comes from a token. A new token is defined in `_tokens.scss` and documented.
- **Override a Frappe variable only inside the `[data-theme]` blocks.** A neutral
  placed in bare `:root` becomes the base that dark mode inherits — that is the
  "light leaks into dark" bug that made the previous theme work only partially.
- **`!important` only in the two sanctioned places** (the `font-family` block and
  `@media print`). Everything else escalates through the `.bunood` class on `<html>`.
- **Comment the why, not the what.** This repo already does this better than most —
  `_tokens.scss` explaining why 0.5px hairlines round the way we want, dark mode
  explaining why values are *selected* rather than lightness-flipped. Keep it. A
  comment that records the incident behind a rule is worth ten that restate the code.
- **Small, single-purpose commits.** The existing history is exemplary here — one kit
  per release, refactors landed separately from behaviour. Keep refactor and behaviour
  change in different commits so a bisect can tell them apart.

### 1.4 Tokens are a versioned contract

- **Unify by redirect, never by deletion.** Layer 3/4 consume token names; deleting one
  breaks every consumer. Aliases stay as aliases pointing at the canonical value.
- **Additive-only.** New tokens are free; renaming one is a breaking change to anything
  downstream that reads it.
- **Delete only what you can prove is unreachable** — grep to zero matches first, and
  record the grep. Dead tokens are real cost, but a token reachable only from a
  customer's brand override looks dead to grep.

### 1.5 Accessibility — the part that is genuinely ours

The layer model says we don't own Frappe's markup. That protection **stops at our own
components**, and that is exactly where the palette, inbox, breadcrumbs and cluster
live. Upstream Desk violations are not ours; ours are.

- **Native element before ARIA.** A wrong `role` has no compiler, no runtime and no
  failing test — it is discoverable only by AT testing. ARIA is a promise the DOM does
  not enforce.
- **Every overlay has a focus contract:** focus moves in on open, is contained while
  open, returns to the invoking element on close, Esc closes. The palette is the
  primary navigation affordance — an overlay that traps focus there is unrecoverable
  without a mouse.
- **Every interactive control has an accessible name.**
- **Focus-visible ring must clear 3:1** against whatever it sits on, in both themes.
- **Status is never colour alone** — an indicator pill needs text or shape too.
- **Motion honours `prefers-reduced-motion`** at the animation primitive, not per
  animation, so new animations inherit it by default.

### 1.6 RTL and Arabic are the default case, not a variant

- Logical properties only — already build-enforced, keep it that way.
- **Isolate bidi runs.** Latin and numeric strings embedded in Arabic (invoice series,
  IBAN, VAT number, unit codes) need `dir="auto"` or `unicode-bidi: isolate`. Without
  it the bidi algorithm reorders the neutral characters around them: trailing
  punctuation jumps sides, a hyphenated series renders backwards. The stored string is
  correct and only the rendering is wrong, so every unit test passes.
- **Verify in all four combinations** — light/dark × LTR/RTL. They fail independently.
- **Decide the numeral policy once** (Western everywhere / Arabic-Indic in Arabic UI /
  documents only) and make the numeric font stack match it. See §2.4.

### 1.7 Verifying

- **Write the check before the change**, and re-measure both sides. A fix you cannot
  demonstrate is a belief.
- **Reproduce before fixing** — except during an incident, where you mitigate first.
- **Trust the observation, but verify the observation is real.** Confirm you are
  running the code you think you are; a stale `dist/` or a cached asset has burned this
  repo before.
- **Baselines must be versioned artefacts, not souvenirs.** A screenshot committed once
  and never updated across three releases is not a baseline.

## Part 2 — Audit, 2026-08-03

### 2.0 Correction: what an earlier pass got wrong

An audit run against the **ops monorepo** (`Desktop/bunood`) concluded this theme had
no CI, no tests, no RTL evidence and an unfixed asset-404. Checked against this repo,
most of that is **false** — the ops repo simply doesn't contain the theme source. What
actually exists here: `ci.yaml` with four gates, a 92-test Playwright suite, `rtl-desk.png`,
content-hashed dist filenames, 62 `aria-` usages, 46 `Escape` handlers, `focus-visible`,
and `prefers-reduced-motion`. The asset-404 recorded in the ops repo's console logs
(`bunood-web.css` served as `text/html`) refers to the **pre-hash filename scheme** and
does not reproduce against current `dist/`.

Recorded because it is the failure mode this document is most likely to repeat: auditing
the wrong tree and reporting absence you didn't verify.

### 2.1 Governance drift — the constitution no longer describes the product

`bunood/docs/design-tokens.md` calls itself the single source of truth and the merge gate
points at it. It documents a **green/gold palette** (`--bnd-primary: #1F5145`,
`--bnd-gold: #C8923C`, `--bnd-ink: #12251F`, flat hex borders).

This repo ships **none of those**. `_tokens.scss` has `--bnd-brand: #4d8756`,
`--bnd-accent: #4463f0`, `--bnd-ink: #16181d`, `rgba()` borders, and derives every
surface with `color-mix()` from a seed that `brand.py` overrides per site. The
documented architecture (fixed palette) and the shipped architecture (seed-derived
surfaces) are different systems.

Two more drifts in the same direction:

- **Decision §4.6** in `plan-theme-upgrade.md` reads "redesign the existing awesombar,
  do **not** build ⌘K from scratch," repeated at §2 phase 5. v0.8.0 shipped a command
  palette kit with its own shell (`palette: Ctrl+K opens our shell with suggestions`).
  Either a deliberate reversal that the decision log should record with its reason, or
  a decision that was overrun.
- The **38-item coverage checklist** driving the last several releases ("item 11",
  "item 12", "item 13", "item 14") exists in neither repo — located 2026-08-03: it
  lives in the *assistant's* per-project memory, along with the versioning policy
  (SemVer pre-1.0, MINOR per item, v1.0.0 at 38/38) and the working method
  (wireframes before implementation, one item at a time). That is a sharper version
  of the drift described above: a roadmap outside any repository is not merely in the
  wrong place, it is invisible to everyone but one participant and is lost the moment
  that memory is. **Action: move it into this repo** as `ROADMAP.md`, and let the
  memory point at it rather than hold it.

**Action:** the token constitution belongs in this repo, next to the tokens it governs.
A governance document in a different repo, describing a palette that no longer ships,
governs nothing.

### 2.2 Contrast: no target is stated, and the defaults already fail

`wcag` appears **zero** times in this repo. `contrast` appears 12 times, all prose or a
preset name (`Dark Contrast`). Nothing states a target level and nothing checks one.

Computed against the **shipped** tokens (`color-mix()` resolved in sRGB, `rgba()` borders
composited over their surface), at the default seed `--bnd-brand: #4d8756`:

| Pair | Ratio | Needs | Note |
|---|---|---|---|
| `ink` / `surface` | 17.76 | 4.5 | pass |
| `ink-muted` / `surface` | 4.83 | 4.5 | pass, but only just |
| `ink-muted` / `pane` | 4.40 | 4.5 | **fail** on tinted surfaces |
| `ink-muted` / `active` | 4.09 | 4.5 | **fail** |
| `ink-subtle` / `surface` | 2.61 | 4.5 | **fail** — see below |
| `ink-subtle` / `page` | 2.49 | 4.5 | **fail** |
| white on `brand` (button label) | 4.27 | 4.5 | **fail at the default seed** |
| `accent` as text / dark `surface` | 3.27 | 4.5 | **fail** |
| `ink-subtle` / dark `surface` | 3.31 | 4.5 | **fail** |
| `border` / `surface` | 1.22 | 3.0 | fine as a separator, **not** as a control's sole boundary |

Two structural findings:

**`--bnd-ink-subtle` is a text token that never passes as text.** 2.61:1 light, 3.31:1
dark, in every brand configuration tested. Either it is documented as decorative-only
(and never applied to text), or it needs to move.

**The brand seed is customer-chosen and nothing validates it.** `brand.py` re-derives
every surface from it. White-on-brand button text across seeds:

| Seed | Ratio |
|---|---|
| `#4d8756` (shipped default) | 4.27 — already failing |
| `#4463f0` (the accent blue) | 4.90 — passes |
| `#C8923C` (gold) | 2.75 |
| `#F5C542` (a bright yellow a customer might pick) | **1.62** |

A build-time contrast check is bypassed entirely by this path. The guard has to live
where the seed is accepted — either constrain the picker to a validated set, or derive
the on-brand ink (`#fff` vs `#16181d`) from the seed's luminance instead of assuming
white.

**Action:** state the target (WCAG 2.2 AA — 4.5:1 body, 3:1 large text and UI/focus
boundaries), publish the measured ratio for every pair the token contract creates, add
a build gate that recomputes them, and add a runtime guard at `brand.py`.

---

#### RESOLVED 2026-08-06 — item 32

**The target is stated: WCAG 2.2 AA.** 4.5:1 for text (every text token in this theme
is below the large-text threshold, so nothing uses that allowance), 3:1 for UI
components, meaningful graphics and the focus ring. Disabled text is exempt under
1.4.3's incidental clause; that is the only exemption claimed by role.

**Everything above was reproduced before anything was changed.** `tools/contrast_gate.py`
was written first and run against the unmodified tokens; it returned 17.76, 4.83, 4.40,
4.09, 2.61, 2.49, 4.27, 3.31 and 1.22 — every figure in the table, independently. That
agreement is the reason to trust what it says now.

It also found three the audit missed: `ink-muted`/`hover` at 4.45, `--bnd-warn` as
status text at 4.01, and — the largest — **`--bnd-brand` is written as TEXT in seven
places** (breadcrumb, dock label, two inbox rules, three sidebar rules), which fails at
exactly the same 4.27:1 as the button label. One in the table is withdrawn: `accent as
text` measures 3.27 but has no call site, `color: var(--bnd-accent)` appears zero times.

**The structural answer: the seed contributes hue, the system controls lightness.**
That is what Material 3 (role pairs pinned to tones), Radix (generated 12-step scales),
Spectrum and Carbon (pick a ramp, not a colour) all do. Nothing is ever rejected —
refusing a tenant's brand produces a support ticket, not an accessible desk. So the
brand now has three roles rather than one:

| token | role | guaranteed |
|---|---|---|
| `--bnd-brand` | washes and hue tints — nothing is read on it | unconstrained, exactly the seed |
| `--bnd-brand-solid` | opaque fills | 3:1 vs every surface **and** 4.5:1 under its label |
| `--bnd-on-brand` | what to write on that fill | not always white — a yellow seed keeps its yellow and takes dark ink |
| `--bnd-brand-ink` | the brand as text | 4.5:1 vs every surface |

`--bnd-ink-subtle` was the other structural finding, and it moved rather than being
documented away: it is on 14 real text rules, so "decorative-only" would have been a
label, not a fix. It is now fitted to 4.5:1 and `--bnd-ink-muted` to 7:1, which keeps
three distinguishable levels instead of collapsing the two lower ones together.

**A fixed value cannot solve this, which is why the fitting is per-tenant.** Every
surface is a mix of the seed, so its luminance — and every ratio measured against it —
moves with a colour the customer picks. Measured across eight seeds, `ink-subtle` failed
in 96 of 96 placements and `ink-muted` in 21. `palette.derive()` fits each ink and fill
against the surfaces that seed actually produces; `brand.py` formats the result and
**`tools/contrast_gate.py` measures that same function**, so CI is not checking a copy.

**What is now mechanized** (`npm run contrast`, and a CI step):

- 1,656 pairs (item 22 added the sidebar pill/mark/stand-down rows): 11 seeds × 2 modes,
  plus the no-brand-stylesheet fallback — what a fresh
  install paints before `after_migrate` runs. The seed list spans plausible brand
  colours and the pathological ends (pure white, pure black, mid grey).
- Token values are *parsed out of* `_tokens.scss`, never restated, and the static
  defaults are asserted equal to `palette.derive()` for the shipped seed — the one
  duplication that cannot be deleted is the one that now cannot drift silently.
- The smoke suite reads `getComputedStyle` off a live desk and feeds it to the same
  Python implementation, so the enforced numbers are tied to pixels once per run.

**The same pairs, after** (light mode, shipped seed). `npm run contrast -- --table`
prints all of them, computed from the current tokens — which is why the command is the
record and this table is only a sample of it:

| Pair | Before | After |
|---|---|---|
| `ink-muted` / `surface` | 4.83 | 8.33 |
| `ink-muted` / `pane` | **4.40** | 7.56 |
| `ink-muted` / `active` | **4.09** | 7.04 |
| `ink-subtle` / `surface` | **2.61** | 5.35 |
| `ink-subtle` / `page` | **2.49** | 5.10 |
| `ink-subtle` / `active` | **2.21** | 4.52 |
| `on-brand` / `brand-solid` — was white on brand | **4.27** | 4.56 |
| `brand-ink` / `surface` — was the brand as text | **4.27** | 5.33 |
| `warn` / `raised` | **4.01** | 5.23 |

**Two things are deliberately measured and not enforced**, with the number published so
the exemption is visible: `--bnd-border` at 1.22:1 (a separator) and `--bnd-border-strong`
at 1.45:1 (a hover accent that always accompanies a background change — both call sites
were read). What is *not* settled is whether a control whose resting boundary is a
1.22:1 hairline is identifiable at all. That is a per-component judgement, not a token
value, and it belongs to **item 34**.

**Still open, and stated rather than quietly excluded:** the sidebar style kit's own
palette (`--bnd-sb-*`, 8 presets with hand-authored hexes at `_sidebar.scss:72`–`108`)
is outside the gate. Its values are fixed rather than seed-derived, so it carries no
per-tenant risk, but it is unmeasured. Tracked under item 34.

**CLOSED, item 22 (2026-08-13).** The hues themselves were fitted and gated as ink on a
pane in 34a slice 2 (28 rows), before this paragraph was ever corrected to say so — and
that fit alone was not enough: it never covered a hue used as a *fill under a label*,
which is how the shipped default failed AA (2.08:1–2.40:1). Item 22 added the missing
rows — the pill fill against every pane, each hue as a mark, the brand pane's
fixed-value stand-down pair — and changed the rule so a hue can never paint a label's
fill again. `SB_FITS_LIGHT`/`SB_FITS_DARK` in `tools/contrast_gate.py` still hand-copy
their 14 hexes out of `_sidebar.scss` rather than deriving them; that duplication is
real but was not a prerequisite for this fix and remains open.

### 2.3 Accessibility: present in the components, absent from the gate

The kits already use ARIA and handle Esc — this is not a greenfield problem. What is
missing is that **none of it is asserted**. The 92 smoke tests cover behaviour
(opening, routing, badges, layering, preview round-trips) and none cover focus order,
focus restore, accessible names, or roles.

**Action:** add focus-contract assertions to the existing suite — they are cheap because
the harness already drives the palette and inbox. Then add the accessibility clauses to
the contribution gate (1.5), and consider `axe` scoped honestly: a hard gate on our own
components, a baseline-diff over Desk pages so only *new* violations fail. An unscoped
axe run over the Frappe Desk will drown in upstream violations and be abandoned.

**CLOSED, item 22 (2026-08-13).** Both halves of the action are built. `tests/smoke.mjs`
now carries a full `a11y:` family — menu focus/keyboard contract, the board's zone and
chip roles, landmarks and `aria-current`, breadcrumbs, the inbox's filter toggles, and a
walked-tab-order ring check — and `assertMotionPrimitive`/`assertRingCoverage` joined
`build.mjs` (§1.1). `axe` is scoped exactly as proposed: a hard gate over `OURS` (now
including the settings surface, with include-coverage tracking so a selector that never
matches is not silently tolerated) plus a baseline-diff over Desk pages that fails only
on *new* violations.

### 2.4 Two concrete defects

**Bidi isolation is absent.** `bidi` — zero hits. See 1.6 for why this bites a bilingual
product specifically.

**The numeral policy is undecided, and the numeric font token will break when it is
decided.** If Arabic-Indic numerals are ever enabled, a numeric stack led by a Latin-only
face falls through to the next family and loses the tabular alignment the token exists
to guarantee — in the KPI and money columns it was created for.

### 2.5 Payload is unmeasured

Current: **78 KB** CSS, **183 KB** JS (`dist/`, uncompressed). These load via
`app_include_css`/`app_include_js` on every Desk page for every user of every tenant,
on top of Frappe's own bundles. One kit has been added per release with no size ever
recorded.

**Action:** record both numbers in each release commit and set a ceiling that requires a
decision to cross. Nearly free, and it makes the growth curve visible before someone
complains.

### 2.6 What is genuinely fine

Said plainly because an audit that only lists problems is not calibrated: the build-time
RTL guard, the dist-drift gate, content-hashed filenames, the console error budget, the
92-test suite, and `verify.mjs` are all *better* than the general practice they
implement. Several of them exist because a specific failure was diagnosed and closed
with a mechanism rather than a habit — which is the thing most teams never get to.

## Part 3 — Practice catalogue (reference)

Condensed from the full general list. Items marked **●** are the ones that bear
directly on this repo; the rest are recorded so the reasoning is available when the
theme grows into a Vue SPA layer or when this doctrine is reused elsewhere.

### Before code exists
● Sharpen the problem statement before the solution · ● Sketch the data model before the
control flow · Do the risky part first · Time-box the spike and decide its disposition
up front · Count unknowns, then give a range · ● Write down what would change your mind
· ● Classify the decision as one-way or two-way door

### Design
● Write the failure mode before the happy path · ● Make every degradation observable (a
fallback that renders *something* is indistinguishable from success) · ● Design APIs so
the incorrect call cannot be written · ● Deep modules, shallow interfaces · ● Version
additively and read tolerantly · Keep compute stateless · Bound every queue · Put an
explicit timeout on every remote call · Contain blast radius · Prefer boring technology
whose failure modes your team has survived

### Writing code
● Optimize for reading · ● Make the change easy, then make the easy change · ● Don't
freeze an interface until you have two real callers · ● Abstract when you can name the
shared fact, not at a fixed count · ● Prefer duplication over the wrong abstraction —
and inline the wrong one back out · ● Name for intent, not mechanism · ● Comment the
why; comment the what when re-deriving it is expensive · ● Delete what you can prove is
unreachable; investigate what merely looks useless · ● Match local conventions on taste,
not on hazards · ● Land cleanup as its own commit

### Correctness
● Classify every failure as a bug, an environmental failure, or bad input, and encode
the distinction · Fail safe, not fast, where a halt is the failure mode · Prevent races
structurally · Assertions and sampled invariants in production

### Testing
● Push tests to the narrowest scope that can still fail for a real reason · ● Coverage
is a floor detector and a worthless ceiling · ● Write a failing test for any bug you
could plausibly reintroduce · ● Test failure paths · ● Deterministic tests — inject the
clock, never sleep to synchronize · ● Property-based testing for arithmetic · Assert
internal invariants for intricate algorithms

### Debugging
● Reproduce before fixing, except in an incident · ● Bisect when it's a regression and
you have a scriptable check · ● Change one variable at a time · ● Trust the observation
— but verify the observation is real · ● Read the whole error message · ● Fix the
instance now, the class in a follow-up · ● Step away when stuck in a wrong framing

### Shipping
● Small, single-purpose diffs · ● Encode checks mechanically rather than in a checklist
· ● Format and lint automatically · ● Make rollback a single always-available command ·
Decouple deploy from release with flags · Emit one wide structured event per unit of
work · Alert on symptoms, not causes · Test restores, not backups · Runbooks written
during calm · Blameless postmortems

### Frontend
● Gate on field percentiles, not a lab score · ● Enforce a size budget per PR · ●
Content-hash assets and handle the stale-chunk case · ● Derive state instead of copying
it · ● The client is untrusted — duplicate every check server-side · ● Assume anything in
the bundle is public · Treat third-party scripts as owned dependencies · Error
boundaries with uploaded source maps

### Accessibility and i18n
● Native element before ARIA · ● Accessibility as a property of the component library ·
● Contrast in the tokens with a build-time check · ● Keyboard pass and visible focus ·
● Focus contract on every overlay · ● Relationships expressed in markup · ● Reduced
motion at the primitive · ● axe as a regression net, not a conformance check · ●
Logical properties · ● Complete parameterized messages, never concatenated fragments ·
● CLDR plural categories · ● Bidi isolation for embedded Latin/numeric runs · ● Locale
resolution order and an explicit missing-key policy · ● Format through `Intl`

### Craft
● Master your tools for flow, not for a headline hours figure · ● Automate on expected
value, not occurrence count · ● Keep a decision log for contested decisions · ● Defend
contiguous blocks — the cost of interruption is the context reload · ● Write the
explanation you'd give a new teammate · ● Decide the stopping condition before you start
· ● Choose work by leverage
